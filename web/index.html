The problem

Almost every application on your machine keeps its data in SQLite — browsers, phones, notes apps, photo libraries. You have dozens of .db files and no way to look inside any of them without installing something.

And the moment you want to compare that data against a CSV, or against what is actually on disk, you need a second tool and a third.

The answer

One binary. One query language. Five sources.

sqlite('file.db', 'table')a table in a SQLite database
files · files('path')the filesystem, walked recursively
csv('file.csv')a CSV file with a header row
tail('file.log')a log file, streamed as it grows
envenvironment variables of the server process

They join to each other. That is the feature the whole tool exists for — everything else zql does, something else already does better.

Why the wire protocol

"Nothing to install" has to include the client.

zql speaks the PostgreSQL v3 wire protocol, so every Postgres client already on the machine connects to it — psql, node-postgres, anything. Thirty years of somebody else's C completing a handshake with a binary whose [dependencies] section is empty. 

$ zql ~/projects

How it is checked

Against other people's implementations, not against itself.

A reader checked against its own output proves self-consistency — which is exactly what a misunderstanding of the format also produces.

Wire protocolreal psql 16.288 acceptance checks
Wire protocolnode-postgres — JavaScript, sharing no code with libpq27 checks
SQLite readerPython 3's sqlite3, which wrote the fixturesbyte-exact
SQL semanticsgolden queries in tests/295 tests

Two of those oracles caught real bugs. INTEGER PRIMARY KEY reads as NULL in every record — the value lives in the cell header, not the row. And a REAL column holding 375.0 stores an integer. Both were plausible enough to survive reading the output; only comparing against sqlite3 exposed them.

The bug that mattered most

A four-kilobyte query could end the server for every connected client.

$ psql -c "SELECT 1+1+1+…+1"   # ~1,750 terms
thread 'zql-connection' has overflowed its stack
exit code 3221225725 — STATUS_STACK_OVERFLOW

A stack overflow is not a panic. It aborts rather than unwinding, so the catch_unwind around each connection cannot contain it — a bystander session on another connection died with it, and the listener stopped accepting.

Fixed by bounding expression depth where the tree is built, which closes binding, evaluation and the drop glue at once. The limit is measured, not guessed: nested calls abort at ~110 levels in a debug build against ~1,750 in release, so the cap is sized against the tighter number. Try SELECT 1+1+… in the console above.

What it does not do

A tool without a limitations section has not been tested.

  • Read-only. No INSERT, UPDATE, DELETE or DDL. zql never opens a file for writing — zero write calls in src/.
  • Simple query protocol only. GUI clients negotiate the extended protocol and are refused with a clear 0A000.
  • WAL databases are refused, not read stale. Committed rows can live only in the -wal sidecar, and returning plausible-but-old rows is worse than refusing.
  • No index use. Every query is a full scan; the filesystem walk is cached per session.
  • Expressions nest at most 50 deep, then 54001.
  • UTC only. The standard library ships no time-zone database.
  • The backend secret is not cryptographically random. There is no RNG in std.
