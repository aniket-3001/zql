How it works

A read-only SQL engine that speaks the PostgreSQL wire protocol, so nothing to install includes the client. 

$ zql ~/Library
zql 0.1.0 — listening on 127.0.0.1:5432

$ psql -h 127.0.0.1        # already on your machine
you=> SELECT ext, COUNT(*) FROM files GROUP BY ext;
TCP :5432  →  wire  →  lexer → parser  →  binder  →  executor  →  sources
                                              │                        │
                              names become indices        sqlite · files · csv · tail · env

Every column name and type is resolved before the first row is read — because the protocol writes the result's shape before its contents. That one rule is why binding is a phase of its own.

How I know it's right

Checked against other people's implementations, never against itself.

A reader checked against its own output only proves it is self-consistent — and self-consistency is exactly what a misunderstanding of the format also produces. So the fixtures are written by Python's sqlite3, and the expected values come from sqlite3 too.

That caught two real bugs. INTEGER PRIMARY KEY reads as NULL in every row — the value lives in the cell header, not the record. And a REAL column holding 375.0 is stored as an integer. Both looked entirely plausible in the output.

Read-only by construction — zero file-write calls in the source. Loopback by default. WAL databases are refused rather than read stale, because plausible-but-old rows are worse than an error. The full limitations list is in the README, because a tool without one has not been tested.
